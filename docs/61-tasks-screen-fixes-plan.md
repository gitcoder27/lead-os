## Locked decisions

### D1. Undo refuses a conflicting action, never partially undoes it

Undo restores the previous writable values only if the current server values of every field that the inverse would overwrite still equal the acknowledged post-action values. Include coupled fields affected by the write: schedule/Later/resurface, owner/status, triage state and waiting-party identity. If any protected field on any task differs, reject the **entire original action** atomically with HTTP 409 and a persistent error toast: **"Could not undo: a task changed since this action. Nothing was undone."** Do not silently skip fields/tasks or offer Force Undo. An unrelated edit outside that field set does not block Undo. Value equality, not historical edit detection, is the contract; changing a value away and back is not itself a conflict.

The comparison and write must occur inside the existing server transaction, after access checks. A client GET followed by PATCH, or an `updatedAt` millisecond comparison alone, is not sufficient. Add an optional, strictly validated expected-state guard to the existing bulk request; existing unguarded callers remain compatible. No schema or data migration. Guard forward writes from this hook against their pre-action field values too, so an inverse cannot be based on a stale preimage. Build Undo's expected postimage from the actual successful response, not `optimisticTask`.

Keep the current Tasks Undo duration and one-shot behavior. Preserve Weekly review's existing session-long inline Undo, but route it through the same guarded operation. Do not announce "Undone", clear lingering rows, or clear a review decision until the inverse succeeds. On conflict keep the review decision, refresh authoritative data and report the refusal. On transport failure retain a retryable Undo until its existing lifetime ends; suppress duplicate in-flight submissions. Undo remains a new domain write, not deletion of history: existing event emission and server-maintained timestamps still apply. Do not invent historical timestamp editing or an undo log.

For concurrent optimistic edits, serialize the optimistic/write/settle lifecycle for overlapping task keys within an auth scope and QueryClient, including list and detail writes; distinct tasks can proceed independently. Rollback only the failed operation's fields on its tasks, never an entire cached list/detail snapshot over newer data. A later refetch or edit must not be overwritten by an older failure. Use operation ownership/versioning for cache patches; do not assume TanStack mutation serialization also serializes `onMutate`. Preserve successful neighboring edits and reconcile from the server. Clear affected failed-action selection/lingering state without clearing unrelated actions. Do not extend Undo to every drawer field in this plan; fix its overlapping rollback using the same lifecycle rules.

### D3. Preserve update drafts in memory, with auth isolation

Use an in-memory draft store keyed by `getAuthScopeKey(user)` + canonical task key + composer context (`mode`, `via`, and developer day when applicable). Drawer and full-page detail share the `task_drawer` context; Standup/My Day drafts do not accidentally cross-post into it. Store body, event type, blocker action, private/shared choice and retry request id together. No localStorage/sessionStorage, server draft API, recovery banner, new setting or discard button. This deliberately survives drawer close, task switching and SPA navigation, **not reload, tab close or a new tab**.

Save every local edit synchronously. Clear on successful posting only for the submitted draft revision; text typed while a request is pending remains as a new draft. Emptying the body removes the unsent draft and resets its metadata on the next mount. Failure preserves text and metadata; an unchanged ambiguous-network retry retains its request id, while a changed payload gets a new id. Scope transition, sign-out (even if logout fails), or session loss clears the old scope. Late callbacks must not recreate it or mutate the new user's drafts. Anonymous drafts are not retained. Deletion/access loss does not auto-post a draft; clear it when deletion or loss of access is confirmed.

The shared composer applies these rules wherever mounted without changing developer-visible payloads. Existing Escape behavior and closing affordances stay; saving a draft adds no confirmation flow. This scope does not turn title/details into autosaved recoverable drafts.
